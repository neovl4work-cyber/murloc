# Отладка MURLOC на реальном устройстве — 19 ноября 2026

## Исходная задача

Баг из v1.15 (запись в CREATION.md «ОСТАЛОСЬ»): на телефоне библиотека плагина
отображается (папки и треки видны), но при нажатии воспроизведения всё падает.
Цель — снять стектрейс, найти причину, починить.

## Хронология проделанного

1. **Код-ревью цепочки воспроизведения** (до подключения телефона):
   `resolveSourceForUrl` → `StreamServer` (NanoHTTPD на 127.0.0.1, Range/206)
   → `SafScanner.open` (openAssetFileDescriptor через рефлексию → provider apk)
   → `SafProvider.openFile`. Проверил `urlEncode` из API (дизассемблировал
   core-9.0.jar) — обычный `URLEncoder.encode(UTF-8)`, корректен.
   Все вызовы в плагине обёрнуты try/catch → по коду «падать некому», нужен
   живой стектрейс.

2. **Подключение adb**: телефон сначала `unauthorized` → пользователь разрешил
   отладку на экране.

3. **Плагин на телефоне не был установлен** (`pm path` пуст, пакет
   `com.badmanners.murglar.plugin.local` отсутствовал) → установил мой v1.15
   (Success). Провайдер ожил, `/crashlog` отвечал «(журнал пуст)».

4. **Запустил фоновую запись logcat** (позже оборвалась при отвале USB,
   периодически перезапускал через `adb logcat -d`).

5. **Жалоба пользователя**: «плагин не подтянулся в приложении, выбор папки
   с музыкой не кликабелен».

6. **Улики из logcat (19:43:09–19:43:12)**: пять запусков
   `FolderPickActivity` (тумбы пользователя) — каждый стартует и умирает
   через ~100 мс, SAF-диалог ни разу не открылся, documentsui не стартовал.

7. **Провайдер в тот период отвечал пусто** («No result found» на `/crashlog`
   и `/last`).

8. **Найдена причина «не кликабельности»**: в 19:41 пользователь установил
   свой старый apk от 12 ноября (107 292 байта, md5 `a9df3501c7f7887a0232f8c276664b63`)
   поверх моего v1.15 — подтверждено сравнением md5 через `pm path` +
   `md5sum`. Старая сборка (до v1.15) умирает в собственном процессе
   мгновенно — это и есть симптом «тыкаешь, ничего не происходит».

9. **Переустановил мой v1.15** в 19:52 (`adb install -r`), размер 149 788
   подтверждён.

10. **Тест пикера v1.15 с adb**:
    - SAF-проводник с устройства работает (запуск `OPEN_DOCUMENT_TREE` из shell
      открывает диалог).
    - `FolderPickActivity` из shell: пикер открылся сразу в `/Music` на
      SD-карте (подтверждено скриншотами). Т.е. v1.15 пикер на Samsung РАБОТАЕТ.
    - Прогнал грант кнопками через `input tap`: «ИСПОЛЬЗОВАТЬ ЭТУ ПАПКУ» →
      системный диалог Samsung «Разрешить доступ к „Music“?» → «РАЗРЕШИТЬ».

11. **Результат гранта НЕ сохранился** (главная незакрытая проблема дня):
    - `/last` = `uri=` (пусто), timestamp обновляется → `PickResultStore.save("")`
      вызывался (read() без сохранений отдал бы `timestamp=0`).
    - В crashlog НЕТ записи `onActivityResult`, которую активность пишет при
      ЛЮБОМ результате → результат до активности не дошёл.
    - `dumpsys package … | grep -A8 "granted URI permissions"` — пусто →
      постоянного SAF-гранта у плагина сейчас НЕТ.
    - Живые записи crashlog — только три одинаковые:
      `launchPicker: documentsui не найден, пробуем общий резолв`
      (ActivityNotFoundException на `com.android.documentsui`) — это ожидаемо:
      Samsung держит SAF-проводник в `com.google.android.documentsui`,
      фолбэк v1.15 отрабатывает и диалог реально открывается (см. п.10).

# Итоги дня (вечер) — достижения и открытые проблемы

## ДОСТИГНУТО (подтверждено на устройстве)

1. **Корень «всё пустое/не находит путь» найден: kotlin-stdlib не входил в apk плагина.**
   murglar-gradle-plugin ИСКЛЮЧАЕТ модуль kotlin-stdlib из зависимостей (задумано: код
   плагина исполняется в процессе хоста). Но FolderPickActivity и SafProvider работают
   в СОБСТВЕННОМ процессе плагина → NoClassDefFoundError: kotlin/jvm/internal/Intrinsics
   при первом вызове → процесс плагина мёртв для любого запроса провайдера.
   Лечение: `implementation(files("libs/kotlin-stdlib.jar"))` (FILE-зависимость не
   подпадает под module exclusions). Класс в apk появился, провайдер ожил.
2. **Корень «SAF не вызывается / результат теряется» найден: флаги активности-трамплина.**
   На OneUI 4 (Samsung A52) `android:noHistory` / `android:excludeFromRecents` убивают
   трамплин под пикером → AMS отдаёт синтетический RESULT_CANCELED (record вида
   `t-1 f` в dumpsys). РАБОЧАЯ конфигурация (проверена): activity ТОЛЬКО с
   `exported=true` + `Theme.Translucent.NoTitleBar`, интент — голый
   ACTION_OPEN_DOCUMENT_TREE + GRANT_READ|PERSISTABLE. БЕЗ setPackage, БЕЗ
   EXTRA_INITIAL_URI (оба тоже давали потерю результата — не бисектилось отдельно,
   убраны пачкой). Грант выдан и сохранён:
   `content://com.android.externalstorage.documents/tree/primary%3AMusic`.
3. **Провайдер отдаёт библиотеку**: list по дереву показывает папки и файлы
   (Samsung, .thumbnails, e-onkyo music, Telegram, skillymiron-*.mp3).
4. **Краш воспроизведения = баг ХОСТА**: `IllegalArgumentException: Cannot coerce
   value to an empty range: 0.0..-1.0` в процессе com.badmanners.murglar2
   (coerceIn на -1, т.е. duration). Написан `fs/AudioDuration.kt` (WAV/MP3/FLAC/M4A —
   парсинг заголовков, на ПК против эталонных 5-сек MP3 даёт ровно 5000 мс).
   Плюс кламп в LocalTrackFactory: durationMs <= 0 → 1000 мс.
5. **Телефон/OneUI здоровы**: минимальное тестовое приложение (uiclick
   PickTestActivity) получает RESULT_OK + URI + persistable grant на этом же
   устройстве. uiclick — рабочий accessibility-кликер (где input tap бессилен).

## ОТКРЫТАЯ ПРОБЛЕМА №1: краш при ОТКРЫТИИ «Моя музыка»

Симптом: хост падает с тем же `coerceIn(0.0..-1.0)` СРАЗУ при открытии библиотеки.
Исключено бисектом (всё на свежем состоянии: хост здоров без плагина, плагин
переустановлен, грант выдан):
- НЕ треки (дерево полностью пустое — `BISECT_NO_TRACKS`, listAudio/listSubdirs
  возвращают emptyList — краш остаётся);
- НЕ поля трека (duration клампится ≥1000; bitrate в API null, не -1; в Node/
  NodeParameters нет числовых полей);
- НЕ очередь хоста (ритуал «снести плагин → хост очухается → вернуть плагин»
  сделан, первое же открытие падает);
- НЕ кэш хоста (кэш очищен, плагин снесён/переустановлен, SERVICE_ID сменён
  local→local2);
- НЕ диагностика в preferences (отключена — краш остаётся).

Следующие шаги (по приоритету):
1. **Проверить этот же apk на BlueStacks** (там тоже Murglar): если НЕ падает —

## 20 ноября — ПОЛНЫЙ ЦИКЛ НА BLUESTACKS РАБОТАЕТ

App Player 1 (Android 11), Murglar 6.12 (murglar2). Всё автоматом, без участия пользователя:

1. **Грант SAF через uiclick-accessibility**: FolderPickActivity → documentsui →
   клик «ИСПОЛЬЗОВАТЬ ЭТУ ПАПКУ» через broadcast → RESULT_OK (в crashlog),

   перезапуск, иначе видны старые (пустые/0:01) значения.
3. **openFile был сломан**: прямое открытие составного tree/document URI
   отклонялось хранилищем → FileNotFound → длительности фолбэк 0:01, поток
   воспроизведения 404. ФИКС: DocumentsContract.buildDocumentUriUsingTree.
   Проверка: content read = 81127+ байт, заголовок ID3.
4. **Длительности**: 0:05 (реальные) после фикса openFile — AudioDuration
   через поток провайдера работает на устройстве.
5. **Воспроизведение**: StreamServer стартовал на 127.0.0.1:41171, крашей 0.
6. requireHost: `callingPackage` на Android 11 может бросать NPE внутри
   AppOpsService.checkPackage для shell/anonymous-uid — читать через runCatching,
   пустой caller трактовать как диагностический (shell).

Осталось: проверить телефон с этой сборкой (возможно, очередь хоста подхватит
треки с реальными длительностями и краш уйдёт сам), убрать бисект-остатки,
релиз v1.16.

## 20 ноября, ночь — БАГ «НЕТ ПЕРЕМОТКИ» (в работе)

Жалоба: «некоторые треки не даёт перемотать». Диагностика на Samsung A52:

1. StreamServer Range поддерживает, это не он.
2. В логе системного виджета (FaceWidget) видно `seekAvailable=false` для
   локальных треков — флаг MediaSession, который хост строит из
   ExoPlayer `isCurrentMediaItemSeekable`.
3. Контрольная папка SeekTest с файлами известных форматов (Samsung):
   - real MP4 (ftyp) — seekAvailable=TRUE
   - MP3 — TRUE
   - OGG — TRUE
   - raw ADTS с расширением .aac — FALSE
   - raw ADTS с расширением .m4a (Яндекс) — FALSE
   Вывод: неперематываются ТОЛЬКО сырые ADTS-потоки.
4. Причина: media3 AdtsExtractor по умолчанию (flags=0) ВСЕГДА отдаёт
   SeekMap.Unseekable — CBR-seeking включается только флагом
   FLAG_ENABLE_CONSTANT_BITRATE_SEEKING на стороне ПРИЛОЖЕНИЯ (хоста).
   Хост закрытый → починить с его стороны нельзя.

РЕШЕНИЕ: трансмуксирование ADTS → настоящий MP4 на лету в StreamServer
(AdtsMp4Transmuxer.kt): ftyp + moov (faststart, полный индекс stco/stsz/stts,
esds с AudioSpecificConfig из первого фрейма) + mdat из raw-AAC полезных
нагрузок фреймов. Индекс строится одним проходом, кэшируется (64 записи),
Range-запросы маппятся на смещения исходника. MP4Extractor перематывает.

Проверено на ПК (TmuxTest, файл пользователя 13 МБ):
- 14290 фреймов @48kHz, длительность 304853 мс — совпала с AudioDuration до мс;
- размер собранного MP4 = totalSize; ftyp на месте; mdat на ожидаемом оффсете;
  stco указывает на начало payload.
Баги по пути: unread() в PushbackCountingStream не уменьшал position
(смещения плыли на +12); payload-оффсет при CRC-фреймах (protection_absent=0)
должен включать 2 байта CRC (headerLen 9, а не 7).

Следующий шаг: проверка на BlueStacks (App Player 1, Android 11) —
установка 9.18, seek по ADTS-треку, затем релиз.

## FLAC-вопрос (21 ноября, день) → v1.16.6 (APK 9.19)

Вопрос «а с FLAC работает?» вскрыл ЕЩЁ один баг serveOriginal: serveFile
читает head (12 байт) отдельным open'ом, а serveOriginal открывал файл
заново С НУЛЯ и добавлял head впереди → первые 12 байт ДУБЛИРОВАЛИСЬ
в теле ответа. MP3/ADTS это терпят (синхропоиск), FLAC — нет: не видит
сигнатуру fLaC → EOFException/UnrecognizedInputFormat на устройстве.

ФИКС: skipFully(stream, head.size) в serveOriginal. Byte-exact на ПК
(ServeTest2: full/range/head12). На BlueStacks свежезалитый FLAC
(zz_flac_fresh2, без кэша) доиграл до конца 2:02/2:02, запрос виден
в логе (okhttp/5.4.0 → StreamServer), Exo-ошибок 0.

Важные находки сессии:
- Хост КЭШИРУЕТ скачанные треки; битые копии из эпохи багов продолжают
  играться после фиксов. Лечение: «Удалить из кэша» (контекстное меню
  трека) или переименование файла (новый id = чистый кэш). Проверять
  свежезалитым файлом — иначе отлаживаешь старьё.
- Логирование запросов StreamServer: requestLog + Log.i через reflection
  (core-модуль не видит android.util.Log напрямую). Плагин грузится в
  ПРОЦЕСС ХОСТА — статика недоступна процессу провайдера!
- FLAC не требует трансмукса (fLaC → serveOriginal); FlacExtractor
  перематывает при известной длине (Content-Length отдаём).

## 21 ноября, день — «m4a без звука» → off-by-one в таблице частот ADTS (v1.16.7, APK 9.20)

Симптом: позиция идёт, звука нет. Лог: `C2SoftAacDec: aacDecoder_DecodeFrame
decoderErr = 0x0005, substituting silence`.

КОРЕНЬ: в AdtsMp4Transmuxer и AudioDuration таблица частот индексировалась
как SAMPLE_RATES[rateIdx - 1] вместо [rateIdx]. ADTS rateIdx=4 = 44100 Гц,
а мы объявляли 48000. Контейнер (mdhd/mp4a) говорил 48k, ASC в esds — 44.1k
(rateIdx копировался как есть) → рассинхрон конфигурации декодера → тишина.
Файлы 48k (rateIdx=3) заодно объявлялись как 44.1k — длительности ADTS
всё это время были занижены на ~9%.

Важно: контракт build(head, stream) критичен — валидатор ValidateIndex
поначалу давал ложный «дрейф +12», потому что сам передавал поток с нуля
вместо skip(12). После исправления валидатора индекс идеален
(0 bad / 0 gaps на 9567 фреймах WARGASM).

Проверка на Samsung: после «Удалить из кэша» (кэш снова был битым —
закачан через 9.19 с этим багом) WARGASM 70% Dead играет, ошибок
декодера 0. Длительности после pull-to-refresh станут правильными
(3:42 вместо 3:24 и т.д.).
